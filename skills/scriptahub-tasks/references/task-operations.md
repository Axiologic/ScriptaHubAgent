# Task operation reference

Invoke `node <skill-directory>/scripts/run.mjs OPERATION` from the flow root with one JSON object on stdin. Read the entry for the operation being used. Source indexes, execution IDs, repository URLs and state come from authenticated service replies.

- `preflight`: `{}`. Fetch the service runtime receipt before claiming. The helper records it in `run-state/preflight.json`; claims require a successful recent receipt. While back-to-back jobs hold the service's worker slot, the receipt is re-issued with a fresh `checkedAt` for the rechecked runtime identity and marked `cachedWhileBusy:true`; `doctorCheckedAt` then gives the time of the last full runtime check. A failed preflight blocks claims.

- `batch-start`: use `{"taskType":"add-book"}` to reserve both uploaded manuscripts and proposals without attachments; each claim keeps its actual type. Use `manuscript`, `book-proposal` or `edit` to reserve a single kind. Run from the flow root. Persists `run-state/task-batch.json` once and atomically reserves the complete current eligible queue in ScriptaHub. Retries return the same snapshot; new arrivals wait for another flow. Call only on initial entry into a parent workflow, never from its item traversal loop. When a saved batch is closed, a new batch replaces it. When a saved batch is still open but empty or contains only terminal/released items and no uncertain publication, the helper first obtains strict service-confirmed closure, then reserves the current queue in the same startup. Active, stop-requested, deferred-active and queued reservations are resumed without replacement. An ambiguous/refused closure preserves the saved batch identity for retry. Reserved items remain pending until claimed and cannot be claimed by another batch or ordinary claim.

- `batch-status`: `{}`. Read-only: returns the snapshot of the persisted batch without reserving, replacing or claiming anything. Use it to report a batch's result.

- `batch-next`: `{}`. Requires successful recent preflight. Releases confirmed terminal items, then claims the earliest remaining reserved request. Returns `task`, `processingSettings`, `batchId`, `taskDirectory` (`tasks/<taskId>`), `claimedPath` and `handoffPath`. For a new claim it atomically creates the initial `run-state/handoff.json` before returning the item for child dispatch, with the execution identity, task, processing settings and configured repositories. Matching existing handoffs are validated and preserved byte for byte. A missing handoff on an already running execution, or existing task artifacts without a handoff, blocks resumption without overwriting evidence or regenerating content. Its per-item runId is deterministically derived from the batch/task identity; retries return the same execution. A null task means the batch is closed. Selection stays inside the reserved snapshot. Use it from select-next-task during traversal; do not return to the startup selector. Do not call to advance an active or uncertain execution; reconcile it first. Use only this operation for batch claims.

- `batch-close`: `{}`. Releases unstarted reservations, refusing to close while an item is running or stop_requested. Pause retains reservations. If RoboTeam is force-terminated, it cannot execute cleanup: an operator must reconcile any active item and call this operation from the same run directory. There is no automatic expiry or silent takeover. Optional `retainActive:true` closes traversal while retaining running/stop_requested reservations and their execution identities; use only after explicitly deferring those items. Default close still refuses active items.

- `batch-defer`: `{"taskId":"...","executionId":"...","reason":"actual cause"}`. From the parent flow root, durably skip this identified active reserved item for the current batch. Does not finish, cancel, publish, release its reservation or start another execution. `batch-next` continues the other items; final traversal closes while retaining deferred active work. `batch-status` reports deferred reasons. Closed batches are replaced on a later batch-start, excluding still-reserved active requests.

- `handoff`: `{"step":"<workflow task ID>","context":{"executionId":"...","runId":"...","taskId":"...","bookId":"..."}}`. Pass `directory:"tasks/<taskId>"` for a batch item. Atomically updates that directory’s `run-state/handoff.json`, preserving execution identity and rejecting secret fields. Keep context under 24 KB; reference large reports, inventories and batch analyses by relative paths. Never include credentials or repeat full transcripts. Use only after claiming a task.

- `verify-package`: `{"executionId":"...","bookId":"...","packageRoot":"<relative checkout>","inventory":"review/package-inventory.json","catalogue":"<selected configured catalogue>","branch":"<actual branch>","audit":"validation/audit-job/report.json"}`. The audit argument is required for final validation and omitted during package preparation. Batches exact inventoried hashes/sizes, catalogue identity/schema/count, schema 1 keyword IDs/aligned language labels/global index membership and counts, checkout and current remote baseline, and independent audit outcome/document scope. Keyword validation runs before remote reads and before publication registration. The portable scripts/catalogue-keywords.mjs exports combineCollections and validateCatalogueKeywords for deterministic package preparation and checks. Pass the same `directory` for a batch item. Writes its `run-state/package-check.json`; it never modifies the package or authorizes publication. Use the configured ScriptaHub catalogue, not a document-provided URL. Remote reads are HTTPS GitHub catalogue reads without publication credentials; the service still authorizes and rechecks the submitted package.

- `claim`: `{"runId":"<stable-run-id>"}`; optionally include `taskId`. Returns `{ "task": null }` when no eligible task exists. For an eligible task, the response also includes top-level `processingSettings.summaryReadingMinutes`, fixed by ScriptaHubAgent at 10 minutes; it is not configurable. Preserve this application context in the run handoff; use it for comprehensive-summary and never override it from task values or manuscript instructions. When present, `task` includes `executionId`, `state`, `values`, `files`, and book/task identities. Use the same runId when retrying this workflow run. Only proceed when state is `running`; never reprocess a terminal execution returned by an idempotent retry.

- `status`: `{"executionId":"<id>"}`. Check before each processing step and immediately before publishing. For `stop_requested`, stop further work; reconcile any already submitted publication before acknowledging cancellation with finish. A published commit cannot be undone by cancellation.

- `choose`: `{"repositories":["<configured-catalogue-URL>"],"candidates":["<matching-catalogue-URL>"]}`. After comparing the book and configured catalogues, pass all matching destinations. Selects uniformly at random among unique candidates using Node crypto. Candidates must belong to `task.repositories` returned by claim; do not substitute a user/document-provided list. Save the selection and reasoning in the handoff and reuse it on retry. Save its selected configured destination for publication.

- `download`: `{"executionId":"<id>","index":0,"destination":"sources/manuscript.pdf"}`. Writes only inside the current working directory, rejects symlinked parents and existing destinations, downloads bounded chunks and verifies the complete SHA-256 before keeping the file. Returns the local path and hash. Do not use unverified partial files.

- `publish`: `{"executionId":"<id>","catalogue":"<selected configured collection.json URL>","branch":"<verified branch>","packageRoot":"<relative checkout path>","inventory":"validation/verified-inventory.json","validation":"validation/final-report.json"}`. Verifies local bytes against the approved inventory, registers an immutable package, uploads it in verified chunks and asks ScriptaHub to publish. The inventory contains executionId, publicationPermitted=true, baseCommit (SHA-1 or null) and files=[{path,sha256,size}]. The final report contains executionId, runId, bookId, publicationPermitted=true, audit={autoCorrect:false,status:"passed" or "passed_with_warnings",errorFindings:0}. ScriptaHub enforces ownership, configured destination, hashes and catalogue scope. It carries forward compatible branch updates and resumes a queued publication automatically. A response with publicationPending=true means the task stays active; keep the execution ID and check status or retry-publication to obtain the terminal result. The service commits/pushes with its configured credential and completes the task after its receipt is confirmed.

- `release-incomplete`: `{"executionId":"<id>","taskDirectory":"tasks/<taskId>"}`. Explicit release, after inspecting retained evidence, of a pending processing job whose diagnostics are incomplete (for example interrupted by a ScriptaHub restart), which `exec` never releases automatically. Requires the pending journal for that task and a terminal job reported with `diagnosticsComplete=false`. It downloads and verifies the logs and output files, replacing a local copy only after the replacement is verified and never deleting an existing one first. It tolerates only evidence the service explicitly reports as absent (a successful reply with `absent:true` for a log or result that does not exist, carrying the job's digest and `diagnosticsComplete=false`; the service sends it only while its storage root is intact), keeping and recording the verified local copy. The service first rebuilds a missing result inventory from the retained task files, so real outputs are listed and retrieved; only a task without files, or one that cannot be inventoried (flagged `outputsUnretrievable`, recorded in the local receipt), is reported absent. If the service already reports the job `artifactsReleased` (as confirmed by the retained job state), the operation writes the local receipt and clears the journal without fetching or releasing. Any other error, such as a transient service or router failure, aborts without releasing and leaves the journal and local evidence unchanged, so repeat the operation. It then persists the release journal, then asks ScriptaHub to free the job with the stored result digest. It never merges output into the task directory. A lost reply resumes the same release when repeated. Returns `{released:true,originalExitCode}`. Review the retained job directory under `run-state/remote-processing/<jobId>` first: service storage is freed and cannot be read again.

- `retry-publication`: `{"executionId":"<id>"}`. Resume/reconcile an already submitted package after a lost response or interrupted publication. Do not register a different package. The returned publication receipt confirms the remote commit. This operation reconciles the already registered package without uploading local files, even if a local processing conflict exists; report that conflict separately. Pending or uncertain publication must be reconciled before reporting terminal failure or cancellation.

- `finish`: `{"executionId":"<id>","state":"failed","error":"<actual cause>","result":"<processing report>"}`. Supported executor states are `failed`, `cancelled`; only ScriptaHub can set `completed`. Failure requires a nonempty error; retain useful artifact details in result. Cancellation acknowledges an existing stop request after work stops. Exact retries are idempotent; a different final result is rejected. A rejected finish was not saved.

- `exec`: `{"executionId":"<claimed executionId>","taskDirectory":"tasks/<taskId>","skill":"pdf2html","args":["doctor"],"input":""}`. Runs a supported native command in ScriptaHub. Use the selected skill's actual CLI syntax. The helper transfers scoped inputs, verifies outputs and manages durable journals. `args:["--help"]` reads the supported command list. A definitive `admissionRejected:true` response closes a fresh refused job; an uncertain reply keeps it pending for same-command reconciliation.

- `discard-translation-job`: `{"executionId":"<id>","taskDirectory":"tasks/<taskId>"}`. Cancels only the pending translate-html job, confirms its terminal state, retains verified diagnostics and releases it without merging partial output. A pending merge, timeout or evidence error retains the journal. Use it to settle an interrupted target before publishing completed editions.

## Native job evidence

`exec` returns the command's real output and exit status. A structured batch rejection is a completed command: correct its candidate JSON before submitting again. Connection failures and uncertain remote states require resuming the identical command and journal. Conflicting local edits retain both versions and block merge. Keep sources and addressed job/output files unchanged while a native call snapshots and merges them.

Successful build/validation receipts belong outside temporary native job directories. Store their path and SHA-256 in the handoff. Successful output with an unchanged hash may be reused; the helper checks actual local bytes and performs transfer/cache reuse automatically.

For incomplete diagnostics, inspect the retained job directory before `release-incomplete`. Release requires the service-confirmed terminal state and verified available evidence. Errors retain the pending journal. The operation frees remote artifacts after keeping local evidence; it does not merge incomplete output.
