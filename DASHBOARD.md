# Book dashboard

The authenticated `/account/dashboard.html` page owns My books, Change requests, Tasks and History. Account security remains on `/account/index.html` in UserPersisto. The catalogue and reader remain public.

The manifest declares `routerAccess.entryPath` as the public server entry. Ploinky validates that declaration against the agent's enabled HTTP routes and uses it when the application is selected for the Router root. The embedded account's sign-out link derives its return destination from the deployed application root and retains the current account page separately for Cancel. Agent-port mounts include their auth selector; dedicated hosts retain the Router's host-bound context. Authentication and logout mutation proofs remain Router-owned.

## Ownership and access

The delegated UserPersisto profile supplies `installationAdministratorId`, the identifier persisted when installation setup completed. ScriptaHub never selects the first visitor, an email address or an arbitrary member of the admin role. Catalogue books are registered once with this owner on authenticated requests; missing provider metadata refuses attribution explicitly. Later catalogue refreshes never replace ownership. New books and forks belong to the authenticated creator, and forks retain their source book ID.

The owner can grant or revoke collaborator access by exact account email. The target must first sign in to ScriptaHub so its verified provider ID is known locally. Collaborators can read private book history, proposals and documents and submit changes; they cannot approve proposals, cancel tasks or manage collaborators. Any authenticated reader can propose a change to an imported public book. Proposal authors can inspect their own submission and its documents after access is revoked, but cannot read other private submissions or submit new changes to the private book.

Access events record the acting account and the recipient separately. Edition submission records the book owner as its actor. Display names (or verified account emails when names are empty) are resolved for presentation; authorization continues to use stable provider IDs. Existing events without a recorded recipient remain explicitly unidentified. Repeated access requests that do not change access do not create activity events.

## Changes and tasks

Submission UUIDs are idempotency keys. Immutable HMAC-signed intake records and document SHA-256 hashes remain in the private inbox. Database registration occurs after complete file publication; retrying the same submission recovers database registration if interrupted. Altered replays are rejected. Only approved SQLite tasks are eligible for execution; receipt files are not execution instructions.

The shared browser/server upload policy allows up to eight PDF, DOC or DOCX documents, 50 MB per document and 100 MB total (decimal bytes). The request reader allows an additional bounded 1 MiB for multipart metadata. The server independently validates sizes and document signatures. Returning from the agreement page carries the stored document bytes into the next draft; missing draft files stop submission explicitly. Validation failures allow retry, while successful submissions remain terminal. Browser UUIDs use Web Crypto randomness without requiring `randomUUID`, so they also work on HTTP LAN deployments. This does not relax Ploinky authentication, browser secure-context requirements for other features, or server authorization.

The dashboard follows the existing `scriptahub:language` event for all eight supported languages and preserves form input when language changes. Browser API URLs are resolved relative to the deployed script location, retaining the Ploinky route prefix and current origin without embedding a deployment hostname, IP or port.

An owner submission is accepted immediately. Another user's submission starts `open`; the book owner or any workspace administrator can accept or reject it, including an administrator reviewing their own contribution. Review preserves decisions on individual annotations. Approving an existing-book change does not create a task or increase the book revision. Several requests can therefore be reviewed against the same published revision.

Any authenticated user with access to a book uses **Request a new edition** or **Submit new edition** to queue one edit task containing all approved requests not already queued, running or published. Task membership and immutable request snapshots are written together in an immediate transaction. The client supplies a UUID idempotency key; a retry returns the same edition, even if new approvals arrived meanwhile. At most one queued/running/stopping task is allowed for that book. Later approvals wait for another edition. Failed or cancelled attempts retain their execution history and their approved requests can be included in a new submission.

The executor receives a `requests` array with each request's approved annotations, values, language, base revision and global document indexes. Rejected annotations are not exposed. Private documents are still read from their original HMAC-signed intake records and SHA-256-verified bytes, under the claimed task's executor identity. One edition produces one validated publication package. Revision increases once, only when ScriptaHub records a confirmed publication receipt. Initial book creation remains a separate manuscript/book-proposal task.

Tasks persist their state, timestamps, result and error fields. Approved manuscript tasks can be claimed through the internal MCP service by a configured executor agent. Claiming moves one queued task to running atomically. Owner cancellation changes queued tasks to cancelled, or running tasks to stop_requested. Workers check status between steps and before publication, acknowledge stopped work as cancelled, and record completed or failed results. Stop is cooperative and cannot undo an already published commit. The UI provides manual refresh; it does not claim instant process termination.

Librarian feedback without a book remains a received open contribution visible to its author; it does not bypass book approval or enter the executable queue. Existing pre-dashboard inbox records remain intact and are not automatically replayed.

## Persistence and interfaces

`/data/dashboard.sqlite` stores books, known identities, collaborators, immutable change payloads, task state and events. It uses WAL, foreign keys, a five-second busy timeout and immediate transactions. Files remain outside the database; downloads require access checks and hash verification. UserPersisto continues to own identity and credentials.

All routes run through the existing authenticated `/api/*` Router rule and signed method/path/query/body verification:

| Route | Behavior |
| --- | --- |
| `GET /api/dashboard` | Current user's books, contributions, tasks and permitted history |
| `POST /api/submissions` | Multipart intake; accepts owner changes without a task; initial book creation retains its task |
| `POST /api/dashboard/review` | Owner-only accept/reject with annotation decisions; does not queue work |
| `POST /api/dashboard/editions` | Atomic explicit edition request for an accessible book; charges the requester, snapshots approved corrections if present, and requires bookId, submissionId and confirmedCost |
| `POST /api/dashboard/access` | Owner-only collaborator grant/removal |
| `POST /api/dashboard/cancel` | Owner-only cancellation of a queued task or cooperative stop request for running work |
| `GET /api/dashboard/files/:submissionId/:index` | Authorized private document download |

Approving corrections only retains them for a future edition. It never spends points or queues generation. Explicit edition and fork requests capture the configured cost and debit the requester through UserPersisto before becoming claimable. ScriptaHub creates tasks; existing Cron jobs invoke RoboTeam workflows. ScriptaHub owns the final push and collection.json update after the workflow robot confirms readiness and independent final validation passes.

## Verification and activation

Run `npm test` in `scriptahubAgent`. Tests use isolated SQLite databases and multiple synthetic identities to exercise creation, imported ownership, collaborator access, proposal approval/rejection, stale revisions, duplicate decisions, private downloads, cancellation and persistence. Provider tests check the installation-owner metadata without granting the reader administrative capabilities.

Activate both updated UserPersisto and ScriptaHub runtimes; restart UserPersisto before ScriptaHub. No persistent data deletion is required. Browser SSO, visual layout and real RoboTeam execution are separate verification gates; the service protocol and configured workflow must be activated before real execution is tested.

## Service execution through Ploinky

The standard AgentServer exposes four `internal` MCP tools: `scriptahub_task_claim`, `scriptahub_task_status`, `scriptahub_task_document_read`, and `scriptahub_task_finish`. AgentServer verifies secure-wire grants; the tool wrapper additionally requires an agent actor/caller/subject match, the expected tool, no browser/delegated user, and an identity listed in `SCRIPTA_EXECUTOR_AGENT_IDS`. The manifest configures `agent:AchillesIDE/roboTeamAgent` by default; installations can explicitly replace the comma-separated canonical identities. Empty or invalid configuration fails closed. No administrator email/password, shared ScriptaHub signing key, private data mount or direct SQLite access is given to robots.

Claim accepts `runId` and optional `taskId`. In one immediate transaction it selects the oldest accepted, queued manuscript and persists `task_executions`, bound to source agent and run ID. The same agent/run recovers the same execution; a terminal execution must not be reprocessed. Other task kinds are left untouched. No eligible task returns `task:null`. Running work is never reclaimed automatically after a crash: an interrupted run needs operator review so a completed push is not silently repeated.

Claim returns form values, identities, original filenames, document indexes and SHA-256 values, never private source paths. The tool also returns the current configured catalogue URLs as task.repositories, loaded and validated before claiming. An empty configured list prevents claiming. For the manuscript workflow, the configured list is the operator-authorized set of publication candidates: the workflow compares the main document and requirements with the collections, resolves the chosen Git repository/branch/content root from real metadata and references, and uses the scriptahub-tasks choose operation to randomly select one of multiple matching candidates without clarification. The selection is preserved across retries; it does not create Git credentials or authorize an unrelated remote. No fixed publication repository or branch is required in the form. Document reads require the owning executor and a running execution, verify the signed intake record against the approved change, reject links and hash mismatches, and return base64 chunks of at most 196608 bytes. The caller assembles and verifies the complete file before use.

The executor's finish operation accepts failed or cancelled, with bounded result/error text. It cannot mark work completed. ScriptaHub owns publication and completes the task only after its Git push is confirmed. A cancellation prevents a new push, but cannot undo an accepted remote commit. A publication with an uncertain outcome must be reconciled before terminal failure or cancellation. Exact repeated finish requests return the saved result; conflicting terminal writes fail.

## Service-owned manuscript publication

ScriptaHub Settings has Repositories and Publication tabs. Publication is an inherent responsibility, not an optional mode. The UI calls only ScriptaHub's administrator-only scriptahub_publication_auth tool. GitHub device authorization and personal-token validation run directly inside ScriptaHub. The existing Ploinky OAuth application's public client ID is configurable with SCRIPTA_GITHUB_CLIENT_ID. Device codes are private, administrator-bound, time-limited and polled at GitHub's interval; slow_down increases the interval. A replaced or disconnected authorization cannot install a stale credential. Access-token expiry is enforced and requires reconnecting; no silent credential fallback is used.

Publication follows GitAgent's credential interface: Identity contains the Git author name and email; Authentication offers GitHub and Token. The saved connection method is restored when opening the tab; without a saved method, Token is selected. Selecting GitHub prepares device authorization and displays its code with “Copy code and open GitHub”. Closing the settings stops browser polling. Token entry and Git identity changes are validated and saved when leaving the edited field or pressing Enter. “Save changes” is scoped to Repositories and never submits Publication fields. Clear stored credentials and Disconnect affect only ScriptaHub's connection. The layout is local to ScriptaHub and does not load GitAgent assets or call its tools.

The publication token, Git author identity, GitHub profile and pending authorization are encrypted with AES-256-GCM in /data/private/publication/access.sqlite. The random encryption key is persisted alongside it in the same agent-owned private directory. Directory permissions are 0700; database and key permissions are 0600. Back up the whole private directory together; losing the key makes the credential unreadable. The key is independent of Router grants and runtime identity rotation. No DPU reference, DPU delegation or GitAgent connection is used or imported. An installation moving from the previous design must explicitly reconnect in ScriptaHub Settings; other agents' credentials are never read or removed. Browser responses expose identity and connection state only, and robots never receive the token. Disconnect clears ScriptaHub access and pending authorization, not the remote GitHub token itself or another application's connection.

GitHub access is stored when authorized. Personal tokens use the common Save changes action; saving repository settings after authentication can still fail independently, and the UI reports that partial outcome. Configured catalogue URLs and refresh interval remain in sources.json; publication identity and credentials belong together in the private access record. Public catalogue refresh does not open or decrypt credential storage. Repository settings can be saved before authentication, but manuscript processing requires readable publication access.

Claim checks that publication is configured and its credential is readable before consuming a manuscript. This is a configuration check, not proof that GitHub will accept a later push: token repository permissions, branch protections and concurrent writes still apply. Publication currently supports GitHub blob/raw catalogue URLs; the configured URL and actual branch determine the remote and content root. No host paths, URLs, IPs, Git credentials or administrator accounts are supplied by the workflow.

The workflow performs conversion, editorial work, review/correction and independent final validation. The last stage calls the scriptahub-tasks publish helper with relative package/evidence paths. It never commits or pushes. package_prepare registers an immutable execution-bound inventory and successful audit-only evidence; package_upload transfers contiguous base64 chunks of at most 65,536 bytes. The service verifies file lengths and SHA-256 values, task/book identity, configured catalogue, original manuscript, catalogue schema, unchanged other books, and resource scope. The package limit is 500 files, 50 MB per file and 512 MB total. Schema 1 and schema 2 are supported without conversion between schemas.

ScriptaHub creates a fresh private Git repository below its /data/publications/executionId, checks the recorded remote baseline, commits only inventoried files, and verifies Git has preserved their exact bytes. It performs a normal non-forced push with its own stored credential scoped to the GitHub HTTPS host. Inherited Git configuration, credential helpers, redirects and local hooks are disabled. Git runs inside ScriptaHub because publication files remain in its private data volume; no additional robot access or shared checkout is granted to another service.

Publication inventory/chunks, the prepared commit and confirmed receipt are persisted in SQLite. A lease serializes publishers without holding a database transaction during network operations. A crashed publisher's lease expires after ten minutes; the same execution can then be reconciled explicitly. retry-publication checks the retained commit against the remote before another push, and accepts a later remote commit that contains it. A persisted receipt can complete the task after an interrupted response. No background replay, force push, merge or reset of user repositories is performed. The terminal completion report contains the destination, branch and confirmed commit; validation reports and local artifacts remain in the workflow working area.

RoboTeam uses the `scriptahub-tasks` skill in `skills`. Its launcher sends service calls through the callback socket of the RoboTeam task runtime mounted at `/workspace/ploinky-runtime` (context version 3); the RoboTeam controller relays them with its service identity and without user delegation. The launcher downloads only into its current working directory. Add/refresh ScriptaHubAgent on the robot and enable its agent-owned skills. Activate the updated ScriptaHub manifest/MCP configuration through Ploinky, then run the manuscript workflow manually or schedule it through the existing RoboTeam Cron tab. Each run processes at most one task. The service does not create a Cron job or poll the inbox. No automatic task replay, database deletion or sample worker is installed.

## Points and approval cycles

The points feature uses the current account, reservation and approval-cycle schema.

ScriptaHub Settings → Points configures separate rewards for approved books and corrections per contributor per published edition, costs for editions and forks, and the validity and reminder schedule for earned rewards. Amounts start at zero. New rewards default to 180 days of validity with reminders 30 and 7 days before expiry. UserPersisto owns the balance, ledger, Stripe per-credit price and checkout configuration. Purchased points and manual awards have no expiration. My account → Points shows the balance, expiring points, and history. Workspace billing administrators can look up a user and make an audited manual award.

New manuscripts and book proposals queue immediately, without a pre-generation approval. An attachment is optional for a description-based book proposal. After RoboTeam generation and independent final validation, the workflow robot decides publication readiness; no administrator approval is required before push. Administrators can also inspect and review correction sets for every book in the workspace. Book owners also review corrections. Approval alone never credits correction points. After confirmed publication, each contributor receives one correction reward per book revision, regardless of how many approved sets were included. Only the immutable requests captured in that edition task qualify; later approvals wait for the next edition. The correction reward and validity are captured from Settings when the edition is requested and retained on retry. A failed or unconfirmed publication pays nothing. Reward requests are durably keyed by contributor, book and published revision, so retries and lost UserPersisto responses cannot duplicate awards. A new-book reward is credited after its approved processing completes and publication is confirmed. Equivalent contributions from the same author share a request. Reviews and retries are tied to the current attempt. The edition and fork costs are fixed at confirmation. A funded task is available to the existing RoboTeam schedule only after UserPersisto confirms the debit. A fork pins the source edition content at submission and publishes its source attribution with the derived book.

On failure or cancellation, a managed task stays blocked until processing and any in-flight publication have been resolved. ScriptaHub then reverses the confirmed debit, restores the request and records a dashboard notice and an EmailAgent notification in the same local transaction. A retry is a new attempt on the same request, with a different task ID. A delayed result from an older execution cannot advance the new attempt. Failed email delivery is retried independently. A rejected editorial review is a final decision for that version.

Deploy the updated UserPersisto and ScriptaHub agent checkouts together. Restart the Router so it registers the new tools and HTTP delegations. Restart both agents and reload the Add book workflow in RoboTeam. The UserPersisto service points tool defaults to the exact `agent:ScriptaHubAgent/scriptahubAgent` principal. Set `USERPERSISTO_SCRIPTAHUB_AGENT_ID` in UserPersisto when the installation assigns a different canonical identity. Stripe Checkout is shown once the existing UserPersisto billing and webhook settings are configured.




## Publication and paid editions

The workflow robot decides when a validated edition is ready to publish. ScriptaHub verifies the package, configured content repository, pinned remote baseline and edition history, then pushes and updates collection.json. No human publication approval is required. New books and forks use a configured repository selected by the flow; revised editions retain their existing repository.

An authenticated user with access to a book can explicitly request a paid new edition, independently of correction approval. The requester pays the configured cost; accepting corrections never debits the book owner. Without pending corrections, the task snapshots an explicit revision request. Such a synthetic request does not earn a correction reward. Generation/publication failures retain the blocking restoration/refund/notification cycle before retry is enabled. Initial book retries queue directly.


## Processing input reuse

The final verified manifest chunk acknowledges availableFiles as manifest indexes whose complete bytes are already present in the job workspace. Clients upload only missing files and still verify their immutable local snapshot. This supports retry without resending complete inputs. On successful artifact release, the service can retain verified copies in its private processing-inputs directory, scoped to the exact executor and execution. Workers receive independent copies rather than links to cached data. The cache is bounded to 64 MiB globally, included in processing quota checks, revalidated on startup and reuse, and evicted by age, quota pressure or task completion. Cache failures fall back to normal upload; failed/incomplete job evidence keeps the existing retention and release behavior. Bare runtime doctor commands do not snapshot or transmit task files.


## Book scope throughout processing and publication

Each RoboTeam item handles only its claimed book and, for a fork, its explicitly pinned source. Repository selection reads catalogue metadata, not the contents of other books. Publication packages are sparse: current-book files, its referenced assets and the required catalogue update. Other catalogue entries remain unchanged. A robot-side Git checkout is not required; the helper verifies the remote baseline directly. ScriptaHub Git publication materializes only validated package paths and preserves unrelated indexed files.

The processing helper excludes package/ unless a command addresses the specific current book. Book metadata must match the claim; one book binding is retained for subsequent status/report commands. Only referenced shared assets are added transitively. Unrelated books, global catalogue data, unreferenced assets and Git internals are not processing inputs. The same boundary applies to every result entry. Pending snapshots outside that scope are rejected; the helper does not migrate, cancel or replace previous-version jobs automatically. Invalid validate-book correction/source-override combinations are rejected before admission rather than repeating an expensive failing transfer.


## HTML-first generation

Description/instruction proposals and HTML forks produce complete HTML books without HTML→DOCX→PDF conversion. Their publication metadata may omit PDF, and missing PDF is not a validation error. The native standalone/imported-reader comparison is used with a preserved authored HTML reference and strict zero-new/zero-existing finding acceptance; candidate hashes must match the final package. The final generated-book audit records scope html_layout_integrity, nativeScope edition_layout_regression and existingFindings=0. A supplied PDF manuscript remains the source of PDF fidelity checks. Existing generated intermediary files from earlier attempts stay private and do not become new-job inputs or publication requirements.


### Book cover preferences

The Create form includes optional multi-select style, color and composition presets (with custom entries), plus a free cover description. Empty selections use automatic art direction based on the actual title, subject, audience and book instructions. The values are stored in the authenticated contribution and passed unchanged to its task. Cover preferences remain separate from content instructions. The new-book flow creates original portrait SVG artwork during packaging, maps the cover and thumbnail to the same local resource, and includes it in the immutable publication inventory. A submitted cover-generation request requires artwork for every published language before push. The flow records its visual brief privately and checks the final cover during independent validation. It uses the current robot model to author vector artwork; no external raster-image provider is configured by this feature.


### Personal points and user administration

The account Points tab always shows the signed-in user's balance, purchases and ledger. It contains no user search, account switcher or administrative award controls. Workspace administrators have a separate Users tab, authorized by the server's session response. It initially lists accounts in pages of 25, searches by name/email, and opens account details from a keyboard-accessible list item. Details contain account identity, roles, join date, the selected account's balance/ledger and the idempotent points-award form. Viewing a user does not change the personal Points view. The user-list and award endpoints deny non-admin access on the server.


Point purchases use UserPersisto's platform-owned price per credit. Administration configures `unitAmountMinor` and `currency` through the dedicated pricing tools; UserPersisto persists them as `USERPERSISTO_CREDIT_UNIT_AMOUNT_MINOR` and `USERPERSISTO_CREDITS_CURRENCY`. For example, EUR 0.05 per credit is `5`, `eur`. There are no packs: the customer enters a positive integer number of credits and sees quantity × unit price before Checkout. The payment amount must fit the provider limits. Stripe credentials and the signed webhook are configured separately. Existing payment intents retain their original price, currency and exact credit quantity. Only a verified paid webhook credits the balance, once. Checkout returns to the existing Dashboard Points page.


### Dashboard points and administration

The product Dashboard contains personal Points (balance, ledger and Checkout) and an administrator-only Administration tab (per-credit pricing, user search, user balances and audited point awards). My Account contains only the embedded account and sign-in/security settings. ScriptaHub delegates pricing reads/writes through dedicated `userpersisto_billing_credit_price_get` and `userpersisto_billing_credit_price_set` tools, which require a current billing-administrator capability and cannot read or modify Stripe credentials. The authenticated `/api/dashboard/points/offer-settings` route validates the price and currency fields before forwarding them. UserPersisto remains the durable authority for prices and balances. Updating a price refreshes the personal offer without changing existing payment intents. Dashboard refreshes retain administration form input. Contribution rules and per-credit pricing share one form with Save and Reset. Reset restores the last confirmed values locally; it does not write or reload settings. Return URLs can point to `account/dashboard.html?tab=points`; administration deep links use `?tab=admin` and never bypass the administrator check.


### Administration and Users tabs

The dashboard keeps personal Points, workspace Administration and Users in separate tabs. Administration owns contribution rewards, edition/fork costs, reward validity, both expiration reminders and per-credit pricing. Its local policy API uses the same points.json and validation as the agent settings tools, and requires an administrator for reads and writes. Users owns account search/list/details, balances, ledgers and manual point grants. Both tabs are admin-only. The agent Configure UI now contains Repositories and Publication; the former Points panel was removed. Tab switching preserves unsaved administrative form input.

The Administration tab uses a single form for contribution rewards, processing costs, expiration reminders and per-credit pricing, with one right-aligned Save and Reset action pair and no reload-price button. Initial reads preserve edits made while loading. Saving validates every field before sending changed pricing to UserPersisto and changed rules to ScriptaHub. Repeated submissions are blocked while saving. These two services do not share a transaction: a pricing success followed by a policy failure is reported explicitly, retains unsaved edits, updates only the confirmed pricing baseline, and retries only the remaining changed settings. Reset restores the latest confirmed baseline without network calls. Pricing tools use authenticated transport for exact Router user delegations while UserPersisto requires the active user’s persisted admin.billing.manage capability for both reads and writes.

Checkout return-page validation uses the public ScriptaHub mount retained by the HTTP server before stripping the route prefix. Both a full mounted request and a Router-stripped request with the expected forwarded prefix accept the same mounted Dashboard Points return URL. Another agent mount or an unmounted return page for a mounted request is rejected before billing. UserPersisto still checks the destination origin against its registered origin policy.

For local Stripe testing, the CLI listener must use the same account and sandbox as UserPersisto’s STRIPE_SECRET_KEY. A different logged-in CLI profile or expired CLI login can leave Checkout paid while the local balance is unchanged. Configure the webhook signing secret emitted by that listener, not a different endpoint’s secret. Billing administrators can recover an existing missed payment with UserPersisto’s userpersisto_billing_checkout_reconcile and the real checkout.session.completed or async-payment event ID; recovery retrieves proof from Stripe and uses the original immutable checkout, never a manual credit award.

Credit Checkout opens a centered native dialog in the Credits tab. It loads Stripe.js from js.stripe.com/endive/stripe.js only when needed, creates a server-priced Elements Checkout Session through UserPersisto, and mounts Stripe’s Payment Element. Site colors and typography are passed through Stripe Appearance options; the dialog is at most 480px wide on desktop, presents the card number above the expiry/CVC row, centers a compact payment button, and scrolls within the mobile viewport. No card data is sent to ScriptaHub or UserPersisto. Stripe receives the persisted account email, so the application asks for no extra identity fields. The displayed payable total comes from Stripe’s session rather than a client-only estimate.

After Stripe confirmation, ScriptaHub POSTs only the session ID to /api/dashboard/points/checkout-status. UserPersisto verifies local ownership before retrieving payment status from Stripe and shares its existing settlement checks and idempotency with webhook processing. The browser stores each pending session ID separately under the current account. The Credits tab checks pending payments every 10 seconds, serializes checks for the same session across tabs, and stops checking each session after confirmed success, failure or expiration. Pending payments allow further purchases with independent checkout identities. The purchase status area shows each payment’s status, amount and credit quantity. A confirmed purchase refreshes the balance and ledger once. Payment-method redirects return to the Credits tab with checkout_session_id for the same server verification. Loading or refreshing the page checks the session in the background. Successful verification refreshes the balance and ledger, clears the pending identifier and closes the dialog. Signed webhooks can settle delayed payments after the user closes the page.
