# ScriptaHubAgent: arhitectură și contract

## Sursa analizată

Shell-ul provine din [Axiologic/ScriptaHub](https://github.com/Axiologic/ScriptaHub), commit `445a2ceabc0a63835e5abd1b287289e85e3c56aa`. ScriptaHub servește pagini statice din `docs/`, catalogul `collection.js`, cititorul și cărțile la `books/<titlu>/bk-<id>/`. Formularul original termina în `mailto:` și păstra numai numele fișierelor selectate; nu încărca manuscrisul. Agentul păstrează rutele și aspectul, iar conținutul cărților vine prin HTTP din sursele publice configurate în `sources.json`, fără clone sau checkout Git. Structura unui repo de conținut este descrisă în [CONTENT-REPOSITORY.md](CONTENT-REPOSITORY.md).

Sincronizarea periodică cere `collection.json` și, pentru schema 2, metadatele cărților noi sau modificate, folosind ETag pentru răspunsuri neschimbate, validează metadatele și activează atomic catalogul compus și `remote-books.json` din directorul privat al snapshotului. În schema 2, paginile de prezentare și Animation sunt generate în agent, iar manifestul și istoricul sunt servite din `book.json`. Maparea `resources` trimite URL-urile vechi la fișierele cu nume lizibile din directorul fiecărei cărți și la asseturile comune. SHA-256 rămâne în metadate pentru verificare. În schema 1, paginile publicate rămân transmise de la sursă. Fiecare rută `books/...` este mapată la sursa ei; serverul descarcă și transmite fișierul cerut fără să-l copieze în snapshot. Resursele relative rămân pe aceeași origine cu cititorul. HEAD și Range sunt transmise sursei, iar formularul Animation primește adaptorul de contribuții autentificate. O eroare de catalog păstrează snapshotul anterior; o eroare a unui fișier cerut la lectură răspunde cu 404/502. Metadatele sunt validate la sincronizare, iar existența fișierelor se verifică la acces. Publisherul actualizează catalogul la schimbarea listei sau metadatelor; fișierele servite din ramuri mobile pot evolua independent de catalog.

## Dashboard and task ownership

The dashboard contract is [DASHBOARD.md](DASHBOARD.md). Router-signed identity and the delegated UserPersisto profile remain the authentication boundary. UserPersisto's recorded installation administrator owns imported catalogue books; the signed-in creator owns new books and forks. A role name or request payload never selects the owner.

Browser submissions save immutable signed provenance and private documents in `/data/inbox/<submissionId>/`. They then register a change transactionally in `/data/dashboard.sqlite`. The database, not the inbox, is the task queue and status authority. Identical retries recover the same change and task. Old inbox records are not automatically replayed.

Owner submissions create accepted changes and queued tasks. Other contributors create proposals without tasks. Only the book owner may accept or reject a proposal. Acceptance verifies its base revision and atomically records the decision, advances the accepted revision and creates a unique task. Accepted revision numbers are instruction history, not proof that a published edition was generated.

Catalogue books remain public through the existing source routes. Newly created books are private dashboard records until a future processing/publishing integration produces their editions. Collaborators may read that book's workspace and propose changes; only owners manage access, queued-task cancellation and cooperative stop requests. Download routes verify book access, signed provenance and document hashes.

Manual or Cron-driven RoboTeam workflows can use the internal Ploinky MCP task executor service to atomically reserve a fixed snapshot of accepted manuscripts or edit requests, then claim and process one reserved request at a time. The flow graph loops through its ordinary steps; RoboTeam has no ScriptaHub batch coordinator. ScriptaHub owns reservation exclusivity and durable results, and the local helper persists the batch identity and separate task artifact directories. New arrivals wait for another batch. Pause retains reservations; force termination requires explicit reconciliation and closure of the batch. Source service identities are allowlisted; browser administrator sessions and user delegation cannot call these operations. ScriptaHub retains exclusive access to SQLite and private intake files. Stop requests are cooperative and must be acknowledged by the owning execution. Claims and terminal reports are durable and idempotent; no crash automatically requeues an execution. No scheduler polls the inbox. EmailAgent still sends only receipt notifications, with its existing retry and duplicate-delivery limitations.

SQLite uses foreign keys, WAL, a bounded busy timeout and immediate write transactions. The API and dashboard read the persisted state across restarts. Source catalogue snapshots, published assets and UserPersisto accounts remain outside this database.

## Manuscript publication boundary

RoboTeam executes transformation and independent book validation. It transfers an execution-bound immutable package through the ScriptaHub MCP tools, without filesystem mounts into ScriptaHub storage or Git credentials. `scriptahubAgent` verifies scope and inventory, then publishes from its private data volume using its own Git credential. GitHub authentication, encrypted credential storage and the Git author identity belong to ScriptaHub’s private persistent volume; publication has no DPUAgent or GitAgent dependency. Only the publication service can complete a manuscript task after confirming its remote commit. SQLite retains chunk uploads, commit identity and receipt for explicit idempotent recovery. Network/Git operations run outside SQLite transactions.

## Processing runtime ownership

ScriptaHubAgent owns the skill sources and dependency preparation rules. RoboTeam selects and mounts skills with its existing catalogue and executes their installed CLIs locally in the robot's ALA sandbox. The robot image contains the prepared runtime and system tools; the application container's libraries are not implicitly shared. Source hashes and platform are checked before CLI execution. There is no remote skill-execution channel or workflow-specific RoboTeam extension. Publication credentials remain exclusively in ScriptaHub's private store; only authenticated service operations access tasks, documents and publication.
